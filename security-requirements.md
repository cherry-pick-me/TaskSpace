# Требования безопасности

Продукт: **TaskSpace** (команда cherrypickme). Пользователи, полномочия, сценарии и значимые данные — в [PROJECT.md](PROJECT.md).

Требования относятся к серверному API. API доступно не только из веб-интерфейса, поэтому требование считается выполненным только при проверке на сервере: скрытие кнопки или блокировка поля в React не являются выполнением, а результат одинаков для запроса из интерфейса и для прямого HTTP-запроса.

## Требования

| ID | Требование | Критерий приёмки | Связанные T / D (позднее) |
| --- | --- | --- | --- |
| SR-01 | Любая операция, кроме входа, выполняется только при действующей сессии; без неё сервер не выдаёт данные команд и задач и не изменяет состояние. | Запросы списка задач команды, конкретной задачи, создания задачи, сдачи результата и решения выполняются трижды: без идентификатора сессии, с несуществующим идентификатором и с идентификатором, полученным изменением одного символа действующего. Все отклонены; в ответах нет названий и описаний задач, текстов сдач, замечаний, имён участников и учётных записей. После серии запросов список задач команды, состояния задач и набор сдач и решений те же, что до неё. Те же запросы с действующей сессией участника выполняются. | — |
| SR-02 | Действие выполняется от имени владельца сессии: автором задачи и автором сдачи становится пользователь текущей сессии, и указать вместо него другого пользователя в запросе нельзя. | Участник создаёт задачу, указав в запросе автором другого участника команды, и отправляет сдачу, указав исполнителем другого участника. В системе не появляется задача, автором которой значится не отправитель запроса, и сдача, автором которой значится не отправитель: запрос либо отклонён, либо сохранён с владельцем сессии в качестве автора. | — |
| SR-03 | Пользователь получает задачи, сдачи и решения только тех команд, в которых состоит; знание идентификатора чужой команды, задачи или сдачи не даёт доступа к ним. | Участник только команды A запрашивает список задач команды B, задачу команды B по её идентификатору и сдачи по этой задаче: все запросы отклонены, названия и описания задач, тексты сдач, замечания и имена участников команды B не возвращаются, в том числе в тексте ошибки. Тот же пользователь получает данные команды A. Пользователь, состоящий в A и в B, получает данные обеих команд. | — |
| SR-04 | Задача создаётся только в команде, в которой состоит автор, и только с исполнителем — другим участником этой же команды. | Попытки создать задачу в команде, где автор не состоит; с исполнителем, не входящим в эту команду; с исполнителем, совпадающим с автором, — отклонены, задача не создана, список задач обеих команд не изменился. Создание задачи в своей команде с другим её участником выполняется, и в сохранённой задаче указаны заданные команда, автор, исполнитель и состояние «Назначена». | — |
| SR-05 | Сдавать результат по задаче может только назначенный исполнитель и только в состояниях «Назначена» и «На доработке». | Автор задачи и участник команды, не назначенный на неё, отправляют сдачу по задаче в состоянии «Назначена»: запросы отклонены, новых сдач нет, состояние осталось «Назначена». Назначенный исполнитель отправляет сдачу по задаче в состоянии «На проверке»: запрос отклонён, ранее сохранённая сдача не изменилась, состояние осталось «На проверке». Назначенный исполнитель отправляет непустой результат по задаче в состоянии «Назначена» или «На доработке»: сдача сохранена, задача перешла в «На проверке». | — |
| SR-06 | Принимать результат или возвращать его с замечанием может только автор задачи и только когда по задаче есть сданный результат на проверке. | Исполнитель и участник команды, не являющийся автором, отправляют решение по задаче в состоянии «На проверке»: запросы отклонены, состояние и набор решений не изменились. Автор отправляет решение по задаче в состоянии «Назначена» и по задаче в состоянии «На доработке»: запросы отклонены, задача не перешла в «Принята». Автор отправляет решение по задаче в состоянии «На проверке»: принятие переводит задачу в «Принята», возврат с непустым замечанием — в «На доработке», возврат без замечания отклонён и состояние сохранено. | — |
| SR-07 | Сохранённые сдачи и решения не изменяются и не удаляются, а принятая задача не возвращается в работу: по задаче можно установить, кто что сдал и какое решение было принято. | После цикла «сдача → возврат с замечанием → повторная сдача» задача содержит обе сдачи и замечание, текст первой сдачи и текст замечания совпадают с отправленными. Запросы, изменяющие или удаляющие сохранённую сдачу либо решение, отклонены, содержимое этих записей прежнее. По задаче в состоянии «Принята» сдача и повторное решение отклонены, состояние осталось «Принята», принятый результат и решение не изменились. | — |
| SR-08 | Отклонённый запрос не изменяет состояние системы: при отказе по полномочиям, по состоянию задачи или по некорректным данным задачи, сдачи и решения не создаются и не изменяются. | Фиксируется состояние: список задач команды с их состояниями, сдачи и решения по каждой задаче. Выполняется серия отклоняемых запросов: чужая задача, недопустимое для действия состояние, несуществующий идентификатор задачи, пустой текст результата, возврат без замечания, начало интервала действий вне разрешённого перехода. После серии те же запросы на чтение возвращают прежние списки и состояния; после перезапуска сервера результат чтения тот же. | — |
| SR-09 | Данные для входа защищены: пароль не возвращается API ни в каком виде и не хранится в базе в открытом виде, а идентификатор сессии выдаётся непредсказуемым. | Ответы на вход, на просмотр списка задач и на просмотр задачи не содержат пароля и его хеша. Поиск по файлу базы строки учебного пароля не даёт совпадений. Два последовательных входа одного пользователя дают разные идентификаторы сессии, и идентификатор не выводится из логина, времени входа или предыдущего идентификатора. | — |

## Защитный смысл требований

Последствия нарушения, из раздела 5 паспорта:

- SR-01, SR-02, SR-09 — действие от чужого имени: посторонний работает с задачами команды, а исполнитель принимает собственный результат под учётной записью автора; сданная работа и решения перестают отражать, кто их сделал.
- SR-03 — чужая команда получает содержание внутренних заданий, сданные решения и замечания; сданный результат можно выдать за свой.
- SR-04 — задача попадает к пользователю вне команды, что раскрывает ему задание и искажает ответственность за работу.
- SR-05, SR-06 — сдача или решение от того, кто не имеет на это полномочий в задаче: чужая работа выдаётся за сданную, а незавершённая — за принятую.
- SR-07 — подмена или потеря истории: исчезает основание решения и возможность установить, что именно было сдано и принято.
- SR-08 — отклонённый запрос оставляет частичные изменения, и состояние задач расходится с решениями участников.

## Охват сценариев паспорта

- Сценарий 1 «Поставить задачу участнику команды» — SR-01, SR-02, SR-03, SR-04.
- Сценарий 2 «Сдать и принять результат» — SR-01, SR-02, SR-05, SR-06, SR-08.
- Сценарий 3 «Вернуть результат и завершить доработку» — SR-05, SR-06, SR-07, SR-08.
- Значимые данные из раздела 5 паспорта: учётные записи и сессии — SR-01, SR-09; команды и состав — SR-03, SR-04; задача и её состояние — SR-04, SR-05, SR-06, SR-08; сдачи и решения — SR-03, SR-07.

## Ссылки на стандарт

Для **SR-03** использован пункт OWASP ASVS `v5.0.0-8.2.2`: доступ к конкретным данным ограничен потребителями, которым он явно разрешён, что закрывает IDOR и BOLA. Пункт применим: задачи и сдачи в TaskSpace адресуются идентификаторами, а членство в команде — единственное основание доступа. По стандарту уточнён критерий приёмки: недостаточно скрыть чужие задачи из списка, проверяется прямое обращение по известному идентификатору чужой задачи.

Дополнительно: общее условие о проверках на сервере опирается на `v5.0.0-8.3.1` (правила авторизации применяются на доверенном серверном слое, а не средствами клиента), требование к непредсказуемости идентификатора сессии в SR-09 — на `v5.0.0-7.2.3` (ссылочные токены сессии генерируются криптографически стойким генератором).

## Предметные правила без SR

Правила продукта, проверяемые, но без самостоятельного защитного смысла; остаются в описании продукта и отдельного реестра не образуют:

- ограничения на длину и формат названия и описания задачи;
- обязательность непустого замечания при возврате — учтена в критериях SR-06 и SR-08;
- порядок сортировки и отображения списка задач.

## Допущения

- Команды, учётные записи и состав команд создаются при подготовке локальной базы и через API не изменяются, поэтому требований к управлению составом команд в наборе нет.
- Срок жизни сессии и явный выход паспортом не предусмотрены; при их появлении в границе продукта набор дополняется отдельным требованием.
- Если членство в нескольких командах будет исключено по разделу 8 паспорта, из критерия SR-03 убирается последняя проверка; формулировка требования и его идентификатор сохраняются.
