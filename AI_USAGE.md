# Использование генеративного ИИ

## Выбор темы, объёма и стека

- Участник: M1
- Задача: сузить тему № 17 «Командные задачи» до небольшого продукта и выбрать стек
- Использование ИИ: Codex предложил несколько вариантов названия, набора функций и стека
- В проект вошло: название TaskSpace, три сценария (назначение задачи, сдача и приёмка, возврат на доработку), серверный стек C#, ASP.NET Core, EF Core, SQLite
- Проверка человеком: название, объём и стек выбраны M1 из предложенных вариантов; стек соответствует основному стеку курса
- Связанный результат: разделы 1, 4 и 9 [PROJECT.md](PROJECT.md)



## Доработка паспорта

- Участники: M1, M2, M3
- Задача: довести черновик паспорта до требований S01
- Использование ИИ: черновик разделов 1–9 сделан M1 с помощью Codex; разбор черновика и правки по принятым командой замечаниям — с помощью Claude Code (M3)
- В проект вошло: исправленный паспорт. Основные изменения:
  - веб-интерфейс убран из обязательного ядра, сценарии можно пройти запросами к API;
  - в списке того, что можно исключить, вместо фильтров и поиска теперь веб-интерфейс, полная история сдач и членство в нескольких командах;
  - в таблицу данных и в источники данных добавлены учётные записи и сессии;
  - уточнены полномочия: нельзя назначить исполнителем себя, задачу нельзя менять после создания, пользователь может состоять в нескольких командах.
- Проверка человеком:
  - замечания обсудили втроём и приняли;
  - вместо простой тестовой страницы решили делать полноценный веб-интерфейс на React, им займётся M2; в обязательное ядро он не входит;
  - отдельно согласовали решения, которых не было в черновике: несколько команд у пользователя, запрет менять задачу после создания, вход через сессию;
  - какие технологии для нас новые (ASP.NET Core, EF Core и React), указали сами;
  - M2: вычитка итогового текста и проверка, что переходы состояний в сценариях не противоречат таблице полномочий.
- Связанный результат: [PROJECT.md](PROJECT.md)

## Проектные решения безопасности S04

- Ответственные за разбор: M1 — сессии и серверный доступ; M2 — React, модель угроз и устаревшая вкладка; M3 — требования, переходы и атомарность.
- Задача: подготовить решения по шаблону S04, связать T → SR → D → будущая проверка и оформить вклад.
- Использование ИИ: Codex использовался как помощник при разборе уже подготовленных материалов: помог сгруппировать вопросы по решениям, предложил варианты формулировок механизмов и будущих проверок и обратил внимание на контрпример с задержанным принятием старой сдачи. Команда самостоятельно выбрала подходящий вариант, перенесла его на TaskSpace и внесла правки по своим требованиям. Код продукта и тесты не создавались.
- В проект вошло: решения D-01–D-05, написанные и адаптированные командой в [security-design.md](security-design.md), уточнения [требований](security-requirements.md), [модели угроз](threat-model.md) и [паспорта](PROJECT.md); [вклад и распределение S04](CONTRIBUTIONS.md).
- Проверка человеком: все три участника прочитали и обсудили комплект. M1 сверил D-01 и D-02 с паспортом, SR-01–SR-04 и ограничениями локального запуска; отдельно подтвердил выбор `Authorization: Bearer`, хеширование сессии и отказ от доверия к ID пользователя из запроса. M2 проверил D-03 и D-05 по ролям, таблице переходов, SR-05 и SR-11; отдельно самостоятельно разобрал контрпример с двумя вкладками и подтвердил, что старое решение R1 не может принять новую сдачу R2. M3 сверил D-04, обновлённые SR-06/SR-10 и модель угроз: `expectedVersion` и `submissionId` проверяются до условного изменения, ошибка записи откатывает статус и историю, а конфликт возвращается без изменения данных. После обсуждения все трое приняли итоговые формулировки, ссылки и разрывы из раздела «Разрывы и незакрытые допущения».
- Результат проверки: командой согласованы содержание D-01–D-05, связи `T → SR → D → будущая проверка`, обновления SR-06/SR-09/SR-10, уточнение паспорта и распределение вклада. Проверка была документальной и содержательной. Запуск API, конкурентные HTTP-запросы, откат реальной транзакции SQLite и проверка DOM пока не выполнялись, поэтому планы будущих проверок не выдаются за свидетельства.



## Серверная основа M1

- Участник: M1.
- Задача: реализовать запускаемую серверную основу S05: модель данных, SQLite и seed, вход, bearer-сессии, проверку членства в команде, чтение и создание задач.
- Решения участника: M1 реализовал структуру solution и сущностей по общему контракту S05, хранение только SHA-256 токена, одинаковый `404` для чужого и несуществующего объекта, проверку исполнителя на сервере с дублированием в CHECK и составных внешних ключах SQLite.
- Использование ИИ: Codex помогал писать тесты и править оформление кода.
- В проект вошло: `src/TaskSpace.Api/` (данные, вход, сессии, доступ, задачи, `/health`), тесты `AuthenticationTests`, `TaskAccessTests`, `PersistenceTests`, `ServerSmokeTests`, раздел 10 `PROJECT.md`.
- Проверка человеком: M1 прочитал весь код сервера и тестов, сам выполнил `dotnet build`, `dotnet test` и запуск по `PROJECT.md` с запросом `/health` и входом. Отказы `401`/`404`/`400` сверил с SR-01–SR-04.
- Связанный результат: [сервер](src/TaskSpace.Api/), [тесты](tests/TaskSpace.Api.Tests/), [локальный запуск](PROJECT.md#10-локальный-запуск), [вклад M1](CONTRIBUTIONS.md#реализация-m1).

- Участник: M2.
- Задача: воспроизводимые HTTP-проверки на SQLite, smoke перезапуска, первая версия команд сдачи и решения для сквозного сценария, минимальный React-клиент.
- Решения участника: M2 определил набор проверок по SR-01, SR-03, SR-07, SR-09 и SR-11, сравнение снимка всей базы до и после отказа, smoke с остановкой настоящего процесса. В клиенте M2 выбрал хранение токена только в памяти, вывод текста через JSX и перечитывание задачи без автоповтора после `409`.
- Использование ИИ: автоматическая генерация при подготовке кода тестов, методов API, клиента и текста протоколов. Инструменты: .NET SDK 10.0.401, xUnit, WebApplicationFactory, Node.js, React, Vite, Vitest, Testing Library.

- Проверка человеком: M2 прочитал тесты, клиент и протоколы [M2_CHECKS](docs/M2_CHECKS.md) и [M2_WEB_CHECKS](docs/M2_WEB_CHECKS.md). Повторил `dotnet test`, `bash scripts/smoke.sh`, `npm --prefix web test` и сборку, проверил клиент вручную в браузере вместе с командой.
- Связанный результат: [вклад M2](CONTRIBUTIONS.md#реализация-m2).

## Сценарии и транзакции M3

- Участник: M3.
- Задача: реализовать D-03/D-04, проверить контрпример R1/R2, откат и конкурентные запросы, сверить результаты M1/M2 с заданием S05.
- Решения участника: M3 отвечает за D-03/D-04 с S04. При реализации он сохранил явную таблицу переходов, выбрал условное обновление с клиентской `expectedVersion` и `submissionId` в `WHERE` вместо `BEGIN IMMEDIATE` и ответ `409` без автоповтора. Определил набор проверок по плану D-04 и центральную цепочку защиты `T-05 → SR-06 → D-03/D-04`.
- Использование ИИ: Claude Code (Claude Opus 5.5) по заданию M3 написал код `TaskWorkflow`/`WorkflowService`, тесты `WorkflowTransitionTests`, скрипт контрпримера и черновик протокола [M3_CHECKS](docs/M3_CHECKS.md). Он указал на режим WAL и `SQLITE_BUSY_SNAPSHOT`, а также на два теста, не проходивших на Windows.
- В проект вошло: `Services/TaskWorkflow.cs`, `Services/WorkflowService.cs`, `Endpoints/WorkflowEndpoints.cs`, `WorkflowTransitionTests.cs`, `scripts/m3-counterexample.sh`, `docs/M3_CHECKS.md`, раздел D-04 «Реализация M3»; исправления двух тестов для Windows.
- Проверка человеком: M3 прочитал весь код и документы, сам повторил `dotnet test` (104/104) и `bash scripts/m3-counterexample.sh` (старое принятие R1 → `409`, R2 осталась на проверке), проверил сценарии вручную в браузере. Объясняет без ИИ, почему в `WHERE` стоит версия клиента, почему транзакция начинается с `UPDATE` и что происходит при сбое вставки истории.
- Связанный результат: [вклад M3](CONTRIBUTIONS.md#реализация-m3), [D-04](security-design.md#реализация-m3-и-фактические-проверки).

## Итоговая проверка перед EK1

Все три участника прочитали весь комплект: `PROJECT.md`, SR, модель угроз, D-01–D-05, код, тесты, протоколы, `CONTRIBUTIONS.md` и этот файл. Связи `T → SR → D → проверка` сверены.
