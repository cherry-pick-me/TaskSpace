## 1. Назначение

TaskSpace помогает небольшим студенческим командам назначать задачи и принимать результаты работы. Автор ставит задачу другому участнику, исполнитель сдаёт текстовый результат, автор принимает его или возвращает с замечанием. Пользователи работают через веб-интерфейс, а собственная логика сервера определяет, кто может выполнить каждое действие и как меняется состояние задачи.

## 2. Граница продукта

**В продукт входит:**

- Серверное HTTP API для всех действий сценариев: вход, просмотр задач своей команды, создание задачи с назначением исполнителя, сдача результата, принятие или возврат.
- Хранение учётных записей, команд и их состава, задач, сдач и решений.
- Проверка принадлежности к команде, полномочий в конкретной задаче и допустимости изменения её состояния.
- Веб-интерфейс на React: вход, список задач команды, создание задачи, страница задачи со сдачами и решениями, действия автора и исполнителя. При нехватке времени может быть исключён (см. раздел 8).

Команды, учётные записи с учебными паролями и состав команд создаются при подготовке локальной базы; через API они не изменяются. Пользователь входит под своей учётной записью, после чего сервер определяет его в следующих запросах. Пользователь может состоять в нескольких командах. Полномочия автора и исполнителя определяются отдельно для каждой задачи; это не постоянные должности участников. В одной задаче автор и исполнитель — разные участники одной команды.

**Внешнее окружение и внешние системы:**

- Браузер пользователя, в котором работает веб-интерфейс.
- Средство отправки HTTP-запросов (например, `.http`-файлы в IDE или curl) для проверки API без интерфейса.
- Локальный компьютер, на котором запускаются сервер и веб-интерфейс и хранится файл базы SQLite.
- Сама работа над заданием выполняется вне TaskSpace; сервис хранит её текстовый результат и решение автора.

**Команда сознательно не реализует:**

- Мобильное приложение, интерактивную доску и перетаскивание задач.
- Файловые вложения, чат, уведомления и календарь.
- Интеграции с GitHub, университетскими системами и мессенджерами.
- Публичную регистрацию, приглашения, смену и восстановление пароля, управление составом команд.
- Подзадачи, зависимости между задачами, автоматическую оценку результатов и аналитику.
- Редактирование, переназначение и удаление задачи после создания, повторное открытие принятой задачи.

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| Участник команды | Пользователь, включённый в команду | Смотреть задачи, сдачи и решения команд, в которых состоит; создавать задачу, назначая исполнителем другого участника той же команды | Смотреть данные команд, в которых не состоит; назначать исполнителем себя или пользователя не из этой команды; менять состав команды |
| Автор задачи | Участник, создавший конкретную задачу | Принимать сданный результат или возвращать его с непустым замечанием | Сдавать результат вместо исполнителя; принимать или возвращать задачу без сданного результата; принимать или возвращать результаты по задачам других авторов |
| Исполнитель задачи | Участник, назначенный на конкретную задачу | Сдавать текстовый результат в состоянии «Назначена» и повторно — в состоянии «На доработке» | Принимать или возвращать результат; сдавать результат по задаче, где он не исполнитель; заменять результат в состоянии «На проверке»; менять автора или исполнителя |

Без входа в систему доступен только сам вход; данные команд и задач не предоставляются. Один пользователь может быть автором одних задач и исполнителем других.

## 4. Сквозные сценарии

### Сценарий 1. Поставить задачу участнику команды

- **Участники:** автор и будущий исполнитель.
- **Начальное условие:** оба состоят в одной заранее созданной команде; автор вошёл в систему.
- **Основные действия:** автор создаёт задачу: указывает команду, название, описание ожидаемого результата и исполнителя. Сервер проверяет, что автор и исполнитель — разные участники этой команды, и сохраняет задачу.
- **Результат:** исполнитель видит поручение и понимает, что нужно сдать.
- **Какие данные или состояние изменяются:** появляется задача с командой, автором, исполнителем и состоянием «Назначена».

### Сценарий 2. Сдать и принять результат

- **Участники:** исполнитель и автор задачи.
- **Начальное условие:** задача находится в состоянии «Назначена»; исполнитель выполнил работу вне сервиса.
- **Основные действия:** исполнитель отправляет по задаче непустой текстовый результат, и задача переходит в состояние «На проверке». Автор читает результат и принимает его.
- **Результат:** работа принята; участники команды видят завершённую задачу и сданный результат.
- **Какие данные или состояние изменяются:** сохраняются результат и решение автора; задача переходит из «Назначена» в «На проверке», затем в «Принята».

### Сценарий 3. Вернуть результат и завершить доработку

- **Участники:** автор задачи и исполнитель.
- **Начальное условие:** задача находится в состоянии «На проверке», автор обнаружил недостатки результата.
- **Основные действия:** автор возвращает результат с непустым замечанием. Исполнитель читает замечание, дорабатывает работу и сдаёт новый текстовый результат. Автор повторно рассматривает его и принимает либо снова возвращает.
- **Результат:** исполнитель получает конкретную обратную связь; при успешной доработке задача завершается принятием результата.
- **Какие данные или состояние изменяются:** сохраняются замечание и новая сдача; задача проходит состояния «На доработке» → «На проверке» → «Принята» либо снова «На доработке». Предыдущие сдачи и решения сохраняются в истории задачи.

Переходы выполняются только соответствующим действием автора или исполнителя. Состояние «Принята» завершает процесс.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Учётные записи, данные для входа и сессии | Для каждого пользователя и его команд | Посторонний входит под чужой учётной записью и действует от её имени: например, исполнитель под учётной записью автора принимает собственный результат | Подмена данных входа позволяет действовать от чужого имени; удаление или недоступность не даёт пользователю войти и участвовать в работе команд |
| Команды и состав участников | Для всех участников команды | Посторонние узнают, кто с кем работает | Неверная запись о членстве (например, при подготовке базы) даёт постороннему доступ к задачам команды или лишает участника доступа; без этих сведений нельзя проверить права и назначить исполнителя |
| Задача: описание, автор, исполнитель, состояние | Для автора, исполнителя и команды | Другие команды узнают содержание внутренних заданий и распределение работы | Подмена исполнителя или состояния искажает ответственность и может выдать незавершённую работу за принятую; удаление теряет поручение, недоступность мешает продолжать работу |
| Сданные результаты и решения автора | Для исполнителя, автора и команды | Другая учебная команда получает сданное решение и может выдать его за своё; замечания раскрывают недостатки работы | Подмена искажает сданную работу или обратную связь; удаление теряет историю сдач и основание решения; недоступность мешает проверить результат и выполнить доработку |

Для демонстрации используются вымышленные учебные команды, учётные записи и пароли, задания и результаты.

## 6. Компоненты и внешние взаимодействия

- **Веб-интерфейс (React).** Работает в браузере: страницы входа, списка задач, создания задачи и задачи с историей сдач и решений. Передаёт API данные входа, данные сессии, параметры просмотра, данные задачи, текст результата и решение с замечанием; показывает полученные данные или сообщение об ошибке. При разработке запускается отдельно от сервера. Недоступные пользователю действия в интерфейсе скрываются, но это не заменяет проверок на сервере.
- **Сервер ASP.NET Core.** Проверяет данные входа, определяет пользователя по сессии, проверяет его членство в команде, роль в задаче и текущее состояние, выполняет действие и возвращает ответ. API доступно не только из интерфейса: запросы можно отправить напрямую, поэтому сервер не полагается на проверки во фронтенде.
- **Entity Framework Core** используется сервером для чтения и записи данных.
- **База SQLite** хранит учётные записи, состав команд, задачи, сдачи и решения в локальном файле. Интерфейс обращается к данным только через сервер.

Основное взаимодействие: браузер с веб-интерфейсом → HTTP API сервера → SQLite; ответ возвращается в интерфейс. Без интерфейса те же запросы отправляются к API напрямую. Внешние сетевые сервисы и фоновые процессы для основных сценариев не требуются.

Актуальный архитектурный вид, точки входа и граница доверия описаны в [модели угроз](threat-model.md).

## 7. Откуда продукт получает данные

Запросы приходят из веб-интерфейса или отправляются к API напрямую; сервер обрабатывает их одинаково.

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| Запрос входа | Учебный логин и пароль | Пользователь | Проверяет учётные данные и открывает сессию |
| Сессия в последующих запросах | Идентификатор сессии | Браузер или другой клиент пользователя | Определяет, от чьего имени выполняется действие |
| Запрос создания задачи | Команда, название, описание, исполнитель | Автор | Создаёт задачу после проверки, что автор и исполнитель — разные участники указанной команды |
| Запрос сдачи результата | Идентификатор задачи, текст результата | Исполнитель | Сохраняет сдачу и переводит задачу в «На проверке» после проверки исполнителя и состояния |
| Запрос решения по результату | Идентификатор задачи, принятие или возврат, текст замечания | Автор | Сохраняет решение и меняет состояние задачи после проверки автора и состояния |
| Параметры просмотра | Идентификатор команды или задачи | Пользователь | Выбирает данные, если пользователь состоит в соответствующей команде |
| Начальные учебные данные | Команды, учётные записи, состав команд | Разработчики при подготовке локальной базы | Задают участников демонстрационных сценариев |

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- HTTP API для всех трёх сценариев; сценарии можно пройти HTTP-запросами без веб-интерфейса.
- Вход под учебной учётной записью и определение пользователя в последующих запросах.
- Разграничение действий по членству в команде, авторству и назначению.
- Просмотр задач своей команды, сдач и решений.
- Создание задачи с назначением другого участника команды.
- Сдача текстового результата назначенным исполнителем.
- Принятие или возврат автором; при возврате обязательно замечание.
- Повторная сдача после возврата.
- Проверка допустимых переходов состояний и сохранение данных между перезапусками.

**Функции, которые можно исключить при нехватке времени:**

- Веб-интерфейс на React; без него сценарии проходятся HTTP-запросами к API.
- Членство одного пользователя в нескольких командах; вместо него каждый пользователь состоит в одной команде, при этом команд в базе несколько.

После исключения сохраняются все три сценария, разграничение по команде, авторству и назначению и значимые данные.

Уточнение S04: полную историю сдач и решений сохраняем в ядре. В ранней версии паспорта её можно было сократить, но это противоречит принятому SR-07 и проверке старого решения после новой сдачи в [D-04](security-design.md#d-04-атомарный-переход-и-неизменяемая-история).

## 9. Стек и путь к первой работающей версии

**Основные технологии:** сервер — C#, ASP.NET Core, Entity Framework Core, SQLite; веб-интерфейс — React.  
**Технологии, новые для команды:** ASP.NET Core, Entity Framework Core и React.  
**Внешние сервисы, необходимые для запуска:** для работы приложения не нужны; при первой сборке пакеты загружаются из NuGet (сервер) и npm (веб-интерфейс). Для сборки нужны .NET SDK и Node.js.  
**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:** локально: сервер и веб-интерфейс на одном компьютере, заранее подготовленные учебные пользователи и команды. API можно проверить HTTP-запросами без интерфейса; основные сценарии от внешних сервисов не зависят.

**Что команда реализует первым, чтобы получить запускаемую версию:** минимальное приложение ASP.NET Core с подключением к SQLite через Entity Framework Core, созданием структуры базы с учебными данными и endpoint, который возвращает сохранённую задачу. Работа подтверждается запуском сервера, запросом к endpoint и сохранением данных после перезапуска. Затем — страница на React, которая получает эту задачу через API и показывает её в браузере. После этого добавляются вход, проверки полномочий и действия сценариев.

На S04 уточнён порядок: вход и проверки D-01/D-02 должны появиться до выдачи данных команды через API. Первый запрос задачи выполняется под учебной сессией. Передача сессии — в заголовке `Authorization: Bearer`; React хранит токен в памяти, после обновления страницы нужен новый вход. Для команд сдачи и решения клиент передаёт прочитанную версию задачи, для решения — также ID сдачи. Сервер проверяет их по D-04. React подключаем после минимального серверного сценария.

## 10. Локальный запуск

### Что готово в M1

ASP.NET Core API с EF Core и SQLite: учебные пользователи и команды, вход, bearer-сессии, просмотр и создание задач. В базе уже есть отдельные таблицы сдач и решений, версия задачи и ссылка на текущую сдачу. В M2 добавлены endpoint сдачи и решения автора с проверкой роли, состояния, expectedVersion и submissionId, транзакционная запись истории и проверки HTTP. В M2 также включён минимальный React-клиент: вход, задачи, история, сдача и решение.

### Требования и запуск

Нужен .NET SDK 10.0.100 или новее в линейке 10.0; `global.json` разрешает актуальные feature-версии SDK 10.0 и исключает preview. При локальной проверке использован SDK 10.0.401. SQLite устанавливать отдельно не нужно: библиотека входит в NuGet-зависимости API. Для серверной части Node.js не нужен; React-клиент требует Node.js 22.12+ и запускается отдельно. При первом `restore` нужен доступ к NuGet.

Все команды ниже выполняются из корня TaskSpace, где находится `TaskSpace.slnx`:

```bash
dotnet --version
dotnet restore
dotnet build
dotnet test
dotnet run --project src/TaskSpace.Api
```

Файлы `packages.lock.json` фиксируют зависимости. Повторяемую установку можно проверить командой `dotnet restore --locked-mode`.

Сервер по умолчанию слушает только локальный адрес `http://127.0.0.1:5080`. Во втором окне терминала:

```bash
curl -i http://127.0.0.1:5080/health
```

Ожидаются HTTP `200`, `Content-Type: application/json` и тело `{"status":"ok"}`. Health открыт без сессии и не возвращает данные пользователей или команд. Сервер останавливается через `Ctrl+C` в окне запуска.

При первом запуске создаётся файл `src/TaskSpace.Api/App_Data/taskspace.db` и учебные данные. Повторный запуск использует тот же файл, не пересоздаёт данные и не дублирует seed. Созданные задачи и действующие сессии сохраняются. База и результаты сборки исключены из Git через `.gitignore`.

Порт можно сменить, например: `dotnet run --project src/TaskSpace.Api -- --urls http://127.0.0.1:5081`. Путь базы настраивается через `ConnectionStrings:TaskSpace` в `appsettings.json` или переменную `ConnectionStrings__TaskSpace`; относительный путь считается от каталога проекта API. Начальная схема создаётся через `EnsureCreated`, миграций пока нет. При изменении схемы в следующих частях проекта потребуется выбрать миграции или подготовить отдельную учебную базу; существующие данные не удаляются автоматически.

| 6 | `frank` | A и B | Проверка членства в нескольких командах |

Задача 1 назначена в команде A. Задача 2 — в B. У задачи 3 в B заранее подготовлена история: первая сдача, возврат с замечанием и повторная сдача на проверке, версия 4. Это учебные записи, а не результат ещё не реализованных endpoint сдачи и решения.

### Вход и запросы

```bash
curl -i http://127.0.0.1:5080/api/auth/login \
  -H 'Content-Type: application/json' \
  --data '{"username":"alice","password":"Study123!"}'
```

При успехе API возвращает `200`, `Cache-Control: no-store` и JSON с полями `token`, `tokenType`, `user` и `teams`. `user` содержит только ID, логин и отображаемое имя; `teams` — только команды вошедшего пользователя. Пароль и хеши не возвращаются. Скопируй значение `token` из ответа в переменную своего терминала:

```bash
TASKSPACE_TOKEN='вставь значение token из ответа входа'

curl -i http://127.0.0.1:5080/api/tasks/1 \
  -H "Authorization: Bearer $TASKSPACE_TOKEN"

curl -i http://127.0.0.1:5080/api/teams/1/tasks \
  -H "Authorization: Bearer $TASKSPACE_TOKEN"
```

Первый запрос возвращает задачу 1: `teamId: 1`, `authorId: 1`, `assigneeId: 2`, `status: "Assigned"`, `version: 1`, `currentSubmissionId: null`, пустые `submissions` и `decisions`. Список содержит задачи доступной команды. Статусы API: `Assigned` — «Назначена», `InReview` — «На проверке», `ChangesRequested` — «На доработке», `Accepted` — «Принята».

Создание задачи:

```bash
curl -i http://127.0.0.1:5080/api/teams/1/tasks \
  -H "Authorization: Bearer $TASKSPACE_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"title":"Учебная задача","description":"Подготовить описание API.","assigneeId":2,"authorId":4}'
```

Ожидается `201` и `Location: /api/tasks/<новый ID>`. Переданный `authorId` игнорируется: автором будет Alice (ID 1), выбранная по сессии. Состояние и версия устанавливаются сервером: `Assigned` и 1. Аналогично игнорируются дополнительные `userId`, `teamId`, `status`, `version` и поля истории. Название и описание должны содержать не только пробелы; максимальная длина — 200 и 10000 символов. Пользовательский текст сохраняется как текст и возвращается в JSON; безопасность его отображения в React ещё требует реализации D-05.

### Отказы и проверки

Без bearer-сессии, с неизвестным или изменённым токеном защищённые маршруты возвращают `401`. Неверный логин или пароль также дают `401` с общей ошибкой. Для Alice список команды B и задачи 2/3 возвращают тот же `404`, что несуществующий объект: `{"error":"Объект не найден."}`. Исполнитель из B (`assigneeId: 5`) и сама Alice (`assigneeId: 1`) при создании в A дают `400`. Отклонённые запросы не создают задачи, сдачи или решения. Ошибки возвращаются как JSON без чужих данных и деталей исключения.

Повторяемые запросы для ручной проверки собраны в [TaskSpace.http](TaskSpace.http). В файл не нужно сохранять действующий токен для коммита; оставь исходную заглушку.

```bash
dotnet test --no-restore
```

Тесты используют отдельные временные файловые SQLite-базы и удаляют только свои тестовые файлы. Они проверяют сессии, принадлежность к команде, подмену автора и состояния, неправильного исполнителя, отказ без изменения данных, ограничения внешних ключей и сохранение базы после перезапуска. `ServerSmokeTests` отдельно запускает настоящий процесс API на свободном локальном порту, проходит HTTP-сценарий, проверяет ограничение размера запроса и перезапускает процесс с тем же файлом базы. Рабочая база `App_Data/taskspace.db` в тестах не используется.

CORS разрешает только `http://localhost:5173`, методы GET/POST и заголовки `Content-Type`/`Authorization`, без cookie credentials. Это подготовка к React, не замена серверных проверок.

Ограничения D-01 сохранены: пока нет срока жизни и отзыва сессий, защиты входа от перебора и сетевого развёртывания с HTTPS. Версия рассчитана на локальные учебные данные.

### Smoke и проверки M2

Из корня репозитория: `dotnet test --logger "trx;LogFileName=m2.trx"`, короткая проверка настоящего HTTP и перезапуска: `bash scripts/smoke.sh`. Обе команды используют новые временные SQLite-файлы, рабочая база не меняется. Условия и ожидаемые результаты: [M2_CHECKS](docs/M2_CHECKS.md).

Успешная сдача возвращает `201`, увеличивает версию и переводит задачу в `InReview`. Автор может вернуть текущую сдачу (`Returned`, обязательное замечание) или принять (`Accepted`); `201` увеличивает версию и сохраняет решение. Чужая команда получает `404`, неверная роль — `403`, устаревшая версия/сдача/состояние — `409`. История доступна только для чтения. Ошибка записи откатывает всю транзакцию.

### React в M2

`npm --prefix web ci`, затем `npm --prefix web run dev`; открыть `http://localhost:5173` при запущенном API. Проверки: `npm --prefix web test`, сборка: `npm --prefix web run build`. Токен только в памяти, текст через JSX, конфликт перечитывает задачу и требует ручного повторения. Создание задачи остаётся в API; минимальные страницы M2 реализованы. Фактические DOM-проверки и границы: [M2_WEB_CHECKS](docs/M2_WEB_CHECKS.md).
