# Проектные решения безопасности

Продукт: **TaskSpace** (команда cherrypickme). Решения относятся к модели из [threat-model.md](threat-model.md) и требованиям из [security-requirements.md](security-requirements.md).

На S04 мы сначала зафиксировали серверные решения для приоритетных угроз `T-01`–`T-05`, затем добавили решения для согласованности истории и планируемого React-интерфейса. Разделы «Будущая проверка» сохраняют план S04. Состояние последующей реализации указано в сводке, в разделе «Локальная реализация M1» и для D-03/D-04 — в разделе [«Реализация M3»](#реализация-m3-и-фактические-проверки); наличие плана не означает успешной проверки всех механизмов.

## D-01. Сессия и серверная идентичность

**Связь:** `T-01`, `T-03` → `SR-01`, `SR-02`, `SR-09`.

**Контекст.** API доступно напрямую, поэтому переданный клиентом `userId` не подтверждает личность. Сервер должен проверить сессию до чтения данных команды и выполнения действия.

**Решение.** При входе сервер проверяет учебный логин и пароль через `PasswordHasher` ASP.NET Core. В SQLite хранится хеш пароля с солью, в ответы он не попадает. При успешном входе сервер создаёт 32 случайных байта через `RandomNumberGenerator.GetBytes`, кодирует в Base64 и возвращает непрозрачный токен сессии. В таблице сессий сохраняются только SHA-256 токена и `UserId`; хеш токена уникален, при коллизии генерируется новый. Обычный SHA-256 здесь используется для случайного токена, а не для пароля.

Клиент передаёт токен в `Authorization: Bearer …`. Это ссылочная серверная сессия, не JWT. Общий обработчик аутентификации хеширует полученный токен, ищет запись сессии и устанавливает пользователя. Все операции API, кроме входа, требуют этот контекст. Отсутствующий, повреждённый или неизвестный токен даёт `401` без предметных данных и записи в базу. React держит токен только в памяти приложения: обновление страницы требует повторного входа. Cookie, URL и `localStorage` для передачи или хранения токена не используются. Для отдельных портов разработки CORS разрешает только точный адрес нашего React-клиента и заголовок `Authorization`; права всё равно проверяются на сервере.

Автор задачи, сдачи и решения берётся только из этого контекста. В моделях запросов нет полей `authorId` и `submitterId`; если клиент добавил их, они игнорируются и не копируются в сущности. Сервер назначает автора и начальный статус сам. Поле исполнителя при создании остаётся входным параметром и проверяется по D-02. Пароли и токены не записываются в журналы запросов; ответы входа помечаются `Cache-Control: no-store`.

**Почему так.** Сервер сам связывает случайный токен с пользователем. Для клиента с HTTP-запросами и React работает один механизм. Браузер не добавляет этот заголовок автоматически при отправке сторонней формы. Непредсказуемость токена обеспечивает криптографический генератор, а не просто различие двух строк. Назначение выбранного API описано в [документации .NET](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.randomnumbergenerator.getbytes).

**Рассмотренные варианты.**

- Серверная сессия в `HttpOnly` cookie тоже применима: JavaScript не читает токен, но нужно сразу проектировать защиту от CSRF, поскольку браузер отправляет cookie автоматически.
- Сессия в заголовке требует явной передачи и повторного входа после обновления страницы, зато удобна для обязательного API и не требует cookie-схемы. Для первой локальной версии выбран этот вариант. XSS всё равно может прочитать токен из памяти; поэтому D-05 нужен при наличии React.

**Ограничения и пересмотр.** Как и в исходном паспорте, пока нет явного выхода и срока жизни сессии: запись действует до пересоздания учебной базы. Обновление страницы удаляет токен из клиента, но не отзывает его на сервере. Украденный действующий токен будет принят — D-01 не доказывает обратного. Это ограничение локальной демонстрации с учебными данными. Перед сетевым развёртыванием нужны HTTPS, срок жизни, отзыв сессий и защита входа от перебора с отдельными требованиями и проверками. Если понадобится сохранять вход между открытиями браузера, пересмотрим выбор в пользу cookie вместе с CSRF-защитой.

**Будущая проверка** (критерии `SR-01`, `SR-02`, `SR-09`):

- **Условие:** есть учебный пользователь, команда и исходный снимок задач; сервер запущен на фиксированной версии.
- **Действие:** выполнить серию из [SR-01, SR-02 и SR-09](security-requirements.md#требования) с отсутствующим, неизвестным и изменённым токеном. Дважды войти; отправить создание со сторонним `authorId`; под действующей сессией открыть собственные данные. Просмотреть способ генерации токена, строки учётных записей и сессий в базе и ответы API. Обновить страницу React.
- **Ожидаемый результат:** отказы дают `401` без данных и предметных изменений; действующая сессия работает. Автором становится владелец сессии. В базе есть хеши паролей и токенов, но нет исходных паролей и токенов; в ответах нет ни пароля, ни его хеша. Два входа дают разные токены; анализ кода подтверждает вызов криптографического генератора. После обновления страницы React предлагает войти, а старый токен в прямом клиенте остаётся действующим: это проверяемое ограничение выбранного варианта.

## D-02. Серверная проверка принадлежности и доступа к объекту

**Связь:** `T-02`, `T-03` → `SR-03`, `SR-04`.

**Контекст.** Идентификаторы команды и задачи приходят от недоверенного клиента. Знание ID чужой команды не должно превращаться в право чтения или создания объекта.

**Решение.** Доступ к команде, задаче, сдаче и решению проходит через одну серверную проверку области доступа. Для чтения запрос сначала связывает объект с командой, затем проверяет членство `currentUser` в этой команде. Для создания задачи сервер проверяет, что текущий пользователь состоит в выбранной команде, а исполнитель состоит в той же команде и не совпадает с автором. Идентификаторы из URL и тела используются только как выбор объекта; они не дают полномочий сами по себе. Проверка находится в API/слое команд, а не только в React.

Для запросов списка используется фильтр по членству, а для запроса одного объекта — тот же фильтр с условием по его ID. Сдача и решение связываются с задачей, а задача — с командой. Если маршрут содержит несколько ID, проверяем всю связь: нельзя взять доступную команду A и подставить задачу B или сдачу другой задачи. Для недоступного и несуществующего объекта возвращаем одинаковый `404` без названий, текстов и имён. Для исполнителя вне доступной команды и назначения самому себе — `400` с общей ошибкой выбора исполнителя. В ответ сериализуются только разрешённые поля, а не сущности EF вместе с учётными записями.

**Почему так.** Один общий путь проверки уменьшает риск, что список будет закрыт, а endpoint по известному ID останется уязвимым. Проверка исполнителя при создании одновременно сохраняет ответственность в сценарии назначения и не позволяет создать задачу в чужой команде.

**Рассмотренные варианты.**

- Полагаться на фильтры React и скрытие кнопок — отклонено: прямой HTTP-клиент обходит интерфейс.
- Читать все объекты и фильтровать только при построении страницы — отклонено: другое место выдачи, например история задачи, легко пропустить. Общий серверный фильтр применяется до подготовки ответа.
- Разнести проверки по каждому контроллеру — допустимо для прототипа, но риск расхождения выше; выбран общий policy/service с endpoint-специфичной проверкой роли и состояния в `D-03`.

**Ограничения и пересмотр.** Состав команд создаётся локально и через API не меняется. При добавлении приглашений или смены состава нужно будет определить момент действия членства и пересмотреть кэширование списка.

**Будущая проверка** (критерии `SR-03`, `SR-04`):

- **Условие:** подготовлены команды A и B, пользователь только A, пользователь обеих команд и известные ID объектов B.
- **Действие:** выполнить критерии [SR-03 и SR-04](security-requirements.md#требования), в том числе чтение решений. Дополнительно смешать доступный ID команды A с ID задачи B и ID задачи A со сдачей другой задачи. Повторить проверки прямым HTTP-клиентом, затем сделать допустимое создание задачи в A.
- **Ожидаемый результат:** обращения к B и ошибочные создания отклонены без названий, текстов и имён; доступ к A разрешён, пользователь обеих команд видит обе; списки до и после отказов совпадают.

## D-03. Серверная авторизация действий и явная модель состояний

**Связь:** `T-04`, `T-05`, `T-06` → `SR-05`, `SR-06`, `SR-08`; атомарность по D-04.

**Контекст.** Один участник может быть автором одной задачи и исполнителем другой. Скрытие действий в интерфейсе не защищает API от сдачи или решения чужим участником.

**Решение.** Команды изменения состояния реализуются как отдельные серверные операции с явной таблицей переходов:

```text
Назначена --submit(исполнитель, непустой текст)--> На проверке
На доработке --submit(исполнитель, непустой текст)--> На проверке
На проверке --accept(автор)--> Принята
На проверке --return(автор, непустое замечание)--> На доработке
```

Перед операцией сервер получает задачу через D-02 и проверяет роль по сохранённым `AuthorId` и `AssigneeId`: сдавать может только исполнитель, принимать или возвращать — только автор. Автор, исполнитель и команда после создания не изменяются. Сдача требует непустой текст, возврат — замечание, содержащее не только пробелы. Произвольного изменения `status` через API нет. Отказ из-за роли даёт `403`, неверные данные — `400`, недопустимый переход — `409`, без предметных изменений. Несуществующие операции изменения и удаления возвращают `404/405`. Проверка состояния и запись выполняются вместе по D-04; одного предварительного чтения недостаточно.

Клиент передаёт версию задачи, которую он просматривал, а в решении автора — ещё и ID рассматриваемой сдачи. Это условия применения команды, а не источник полномочий: сервер проверяет их связь и актуальность по D-04.

**Почему так.** Роль — свойство конкретной задачи, а не постоянная должность участника команды. Явная таблица переходов делает запрет принятия незданной работы и повторной сдачи на проверке видимым в коде и тестах. Серверная проверка остаётся действующей при запросе напрямую.

**Рассмотренные варианты.**

- Определять доступ по общему полю `isAdmin` участника — не подходит: в продукте один человек может быть автором одной задачи и исполнителем другой.
- Разрешить любой переход, если пользователь состоит в команде — отклонено: это ломает ответственность и `T-04`/`T-05`.
- Хранить переходы только в React — отклонено: интерфейс не является доверенной границей.

**Ограничения и пересмотр.** Первая версия не поддерживает отмену или повторное открытие принятой задачи. Если появятся новые состояния (например, «Отменена»), переходы и критерии `SR-05`–`SR-08` нужно расширить одновременно.

**Будущая проверка** (критерии `SR-05`, `SR-06`, `SR-08`):

- **Условие:** задача создана с разными автором и исполнителем и последовательно переведена в состояния из таблицы переходов.
- **Действие:** отправить сдачу автором и неисполнителем; сдачу исполнителем в состоянии «На проверке»; принятие исполнителем и возврат неавтором; затем штатную сдачу, принятие, возврат с замечанием и возврат без замечания.
- **Ожидаемый результат:** недопустимые команды отклонены без новых записей и изменения состояния; допустимые переходы дают ровно состояния «На проверке», «Принята» и «На доработке» по таблице; возврат без замечания отклонён.

## D-04. Атомарный переход и неизменяемая история

**Связь:** `T-04`, `T-05`, `T-06` → `SR-05`, `SR-06`, `SR-07`, `SR-08`, `SR-10`.

**Контекст.** Повторная отправка и почти одновременные запросы могут пройти раздельную проверку состояния. Тогда в истории появляются две взаимоисключающие сдачи или решения либо запись не соответствует статусу задачи.

**Решение.** В задаче есть целочисленная `Version`, начинающаяся с 1 и увеличиваемая при каждом переходе. Чтение возвращает её клиенту. В командах сдачи и решения обязательно поле `expectedVersion`; решение автора также содержит `submissionId`. Сервер проверяет права по D-02/D-03, затем в одной транзакции:

1. Проверяет состояние, совпадение `Version` с `expectedVersion` и, для решения, что `submissionId` относится к этой задаче и является текущей сдачей на проверке.
2. Условно обновляет задачу: `WHERE Id = taskId AND Version = expectedVersion AND Status = исходный_статус`, увеличивая версию на 1. Нельзя подставлять в условие новую версию вместо присланной клиентом.
3. При одной изменённой строке добавляет сдачу либо решение с серверным автором; решение ссылается на конкретную сдачу. Для сдачи обновляет ссылку на текущую сдачу. Все эти записи входят в ту же транзакцию.
4. Фиксирует транзакцию и только затем возвращает успех. Если обновлено 0 строк, откатывает её и возвращает `409`; при ошибке вставки также откатывает всё.

Сдачи и решения хранятся отдельными записями без операций редактирования и удаления. Уникальность `Decision.SubmissionId` допускает только одно решение на сдачу, внешние ключи сохраняют связи. Новая сдача получает новый ID, предыдущая остаётся в истории. Для SQLite версия управляется приложением; здесь не предполагается автоматически обновляемый SQL Server `rowversion`. Такой способ поддерживается [EF Core](https://learn.microsoft.com/en-us/ef/core/saving/concurrency).

**Почему так.** Транзакция отвечает за отсутствие частичной записи, а условие по версии — за то, что два запроса не применятся к одной версии. Нельзя ограничиться словом «транзакция»: без проверки версии устаревший запрос может оказаться формально допустимым.

### Пограничный случай: старое решение и новая сдача

**Первое предположение:** достаточно проверить автора и состояние «На проверке», а затем атомарно сохранить решение. Для одной сдачи это выглядит правильно.

**Контрпример:** автор открыл сдачу R1, версия задачи 2, в двух вкладках. Во второй вкладке он вернул R1: версия стала 3. Исполнитель сдал R2: снова «На проверке», но версия уже 4. Теперь первая вкладка отправляет старое «принять R1». Если сервер проверит только автора и статус или возьмёт свежую версию при обработке запроса, он примет R2, которую автор ещё не прочитал. Гонки одновременных запросов здесь даже не требуется.

**Уточнение цепочки:** T-06 включает задержанное действие из прошлого цикла; SR-06 связывает решение с рассматриваемой сдачей; SR-10 требует отклонять устаревшую команду и после повторного входа в то же состояние. Поэтому D-03/D-04 передают и проверяют именно клиентскую `expectedVersion` и `submissionId`. Старое действие с версией 2 и R1 получает `409`, R2 остаётся на проверке. Версия не заменяет проверку полномочий.

| Вариант | Гарантия и цена для TaskSpace |
| --- | --- |
| Условное обновление по версии внутри короткой транзакции | Один запрос изменяет ожидаемую версию; проигравший получает конфликт. Не нужно удерживать блокировку во время просмотра страницы. Клиент обязан обрабатывать `409` и перечитывать задачу. |
| Захват права записи в SQLite до чтения (`BEGIN IMMEDIATE`) | Другой писатель ждёт или получает ошибку занятости, затем состояние перечитывается. Подходит для маленького локального сервера, но право записи общее для файла базы: задерживаются и другие задачи. Клиентские версия и ID сдачи всё равно нужны против устаревшей вкладки. |

Выбираем первый вариант: операции короткие, конфликт явно виден пользователю, а ожидание человека не связано с блокировкой базы. Он не обещает параллельную запись в SQLite: при занятой базе возможен отказ без предметных изменений. Если при проверках нормальные действия часто завершаются занятостью, пересмотрим порядок транзакций или движок БД. Автоматически перечитывать свежую версию и повторять старое решение нельзя: это снова создаст контрпример с R2.

**Будущая проверка** (критерии [SR-06–SR-08 и SR-10](security-requirements.md#требования)):

- **Условие:** файловая SQLite-база и два независимых HTTP-клиента/контекста БД, задача «Назначена», другая «На проверке». Оба клиента прочитали одинаковые версии; состояние до опыта сохранено.
- **Действие:** с общей точкой старта отправить две сдачи; в отдельном опыте — принятие и возврат одной сдачи. Повторить последовательность R1 → возврат → R2 → старое принятие R1. В отдельном опыте вызвать контролируемый сбой записи истории после обновления задачи, но до commit. Проверить историю, затем перезапустить сервер и перечитать базу.
- **Ожидаемый результат:** при каждой паре конфликтующих команд фиксируется ровно одно действие и прирост версии на 1; второй запрос даёт конфликт (при занятости SQLite допустим отказ без записи). Старое решение не закрывает R2. При сбое до commit и статус, и версия, и история остаются прежними. После перезапуска данные совпадают. Свежая команда с версией 4 и R2 принимается; старая история не меняется. Эти проверки нужны на реальной SQLite, а не только на подмене БД в памяти.

**Ограничения и последствия.** Команда не повторяется автоматически после конфликта; React показывает обновлённую задачу и предлагает заново решить действие. После потери ответа клиент сначала читает историю: уже записанная операция могла завершиться успешно. Неизменяемость гарантируется через API, а не против администратора с доступом к файлу SQLite. Полную историю сохраняем; вариант её сокращения из раннего паспорта несовместим с текущим SR-07.

### Реализация M3 и фактические проверки

**Что реализовано.** Переходы D-03 заданы одной таблицей [`TaskWorkflow`](src/TaskSpace.Api/Services/TaskWorkflow.cs): четыре строки «исходный статус, действие, роль, новый статус»; всё, чего нет в таблице, отклоняется. Сдачу и решение выполняет [`WorkflowService`](src/TaskSpace.Api/Services/WorkflowService.cs):

1. Предварительное чтение задачи через фильтр членства D-02 только выбирает ответ: `404` для чужой или отсутствующей задачи, `403` для неверной роли, `400` для пустого текста, неизвестного действия или возврата без замечания, `409` для перехода вне таблицы, чужой версии или не текущей сдачи.
2. Решающая проверка — первый оператор транзакции: `UPDATE Tasks SET Status = новый, Version = Version + 1 WHERE Id = taskId AND Version = expectedVersion AND Status = исходный AND <роль> = currentUser AND <членство>`; для решения добавляется `AND CurrentSubmissionId = submissionId`. В условие подставляется версия клиента, а не прочитанная сервером.
3. Если изменена не одна строка, транзакция откатывается и возвращается `409`. Иначе в той же транзакции вставляется сдача (и ссылка на неё как текущую) либо решение, затем commit.
4. Нарушение уникальности решения на сдачу и занятость SQLite (`SQLITE_BUSY/LOCKED`) превращаются в `409` после отката. Любая другая ошибка до commit откатывает статус, версию и историю и даёт общий `500`.

Endpoint-ов изменения и удаления сдач и решений нет. API-контракт M2 сохранён: `kind` = `Accepted`/`Returned`, повтор после `409` выполняет только пользователь.

**Уточнение сравнения с `BEGIN IMMEDIATE`, выявленное при реализации.** EF Core создаёт базу в режиме WAL (проверено по заголовку файла и наличию `-wal`/`-shm`). В этом режиме обычная (`DEFERRED`) транзакция, начатая с чтения, работает со снимком данных. Если до её первой записи другой запрос зафиксировал изменение, запись сразу получает `SQLITE_BUSY_SNAPSHOT`, и ожидание по таймауту не помогает. Схема «прочитать в транзакции, затем записать» дала бы вместо понятного `409` ошибку занятости. Поэтому в реализации транзакция начинается сразу с условного `UPDATE`, а все проверки, влияющие на запись, находятся в его `WHERE`. Первый оператор берёт право записи и видит последнюю зафиксированную версию. Второй писатель ждёт короткую транзакцию первого (до `Default Timeout=5`) и затем меняет 0 строк. По гарантиям это близко к `BEGIN IMMEDIATE` для одной операции, но блокировка не берётся до валидации входа и не удерживается на время предварительного чтения. Выбор условного обновления сохраняется; ограничение — запись в SQLite остаётся последовательной для всего файла. Пересматриваем при появлении нескольких операторов чтения перед записью в одной транзакции (тогда нужен `BEGIN IMMEDIATE`) или при частых `409` из-за занятости, а не из-за версии.

**Свидетельства** (2026-10-05, Windows 10, .NET SDK 10.0.401, файловая SQLite; команда `dotnet test`; результат 104/104, шесть повторных прогонов подряд без падений). Тесты M3 — [`WorkflowTransitionTests`](tests/TaskSpace.Api.Tests/WorkflowTransitionTests.cs), протокол — [M3_CHECKS](docs/M3_CHECKS.md):

- таблица переходов: ровно четыре допустимых перехода, остальные 8 сочетаний статуса и действия отклоняются;
- контрпример R1/R2: старое принятие R1 с версией 2 → `409`, R2 остаётся текущей сдачей «На проверке» с версией 4, база не изменилась; задержанная сдача прошлого цикла → `409`; после перезапуска история R1 → возврат → R2 → принятие полная;
- роли и состояния: сдача в «На проверке», сдача автором и неназначенным, решение исполнителем и неавтором, принятие без сдачи, по старой и несуществующей сдаче, неизвестное действие, возврат без замечания — отказ без изменений;
- одновременные принятие и возврат одной сдачи (3 повтора): ровно один `201`, второй `409`, версия 5, одно решение;
- сбой вставки сдачи или решения после условного обновления задачи → `500`, статус, версия и история прежние;
- дубликат решения, отклонённый уникальным индексом → `409` без изменений.

Тот же контрпример воспроизводится на работающем сервере скриптом [`scripts/m3-counterexample.sh`](scripts/m3-counterexample.sh): фактически получено `409` на старое принятие R1, затем `"status":"InReview","version":4` с текущей R2 и `201` на новое решение по R2.

## D-05. Вывод пользовательского текста как текста

**Связь:** `T-07` → `SR-11`.

**Контекст.** React остаётся планируемой частью продукта и отображает значения, введённые участниками. HTML или JavaScript в этих значениях не должны получить контекст страницы другого пользователя.

**Решение.** В React названия, описания, сдачи и замечания выводятся обычными JSX-выражениями внутри текстовых элементов. `dangerouslySetInnerHTML`, ручная вставка HTML и преобразование Markdown в первой версии запрещены. API возвращает JSON с корректным типом `Content-Type`; сервер не объявляет пользовательское значение доверенной разметкой.

**Почему так.** В продукте нет требования к форматированию, поэтому текстовые узлы сохраняют исходный результат без отдельного очистителя HTML. Скрытие опасных символов на входе меняет результат пользователя и не заменяет безопасный вывод. Опасность передачи недоверенной разметки в `dangerouslySetInnerHTML` отдельно описана в [документации React](https://react.dev/reference/react-dom/components/common#dangerously-setting-the-inner-html).

**Ограничения и пересмотр.** Решение действует только для текстового интерфейса. При добавлении форматированного текста потребуется отдельная модель разрешённой разметки, sanitizer и новые критерии приёмки. Если React исключён из итоговой версии, `D-05` и `SR-11` пересматриваются вместе.

**Будущая проверка** (критерий `SR-11`):

- **Условие:** React-версия собрана на фиксированной версии; участник может сохранить название, описание, сдачу и замечание.
- **Действие:** в каждое поле записать строку с HTML-тегом и обработчиком JavaScript; открыть задачу другим участником.
- **Ожидаемый результат:** значение видно как текстовый узел, исполняемый элемент не создаётся, обработчик не запускается, сессия и состояние API не изменяются.

## Разрывы и незакрытые допущения

1. Для приоритетных T-01–T-05 определены решения и проверки: D-01/D-02 обеспечивают идентичность и доступ, D-03/D-04 — допустимость действия и отсутствие частичных изменений. Механизмы D-01–D-04 реализованы в API и проверены автоматическими тестами на файловой SQLite (см. «Реализация M3»); это свидетельства для текущей локальной версии, а не для сетевого развёртывания. Ограничение T-01 при краже действующего токена явно остаётся в модели и D-01.
2. `T-06` был отмечен в S03 как средний и не входил в приоритетный набор, но на S04 добавлен `D-04`, поскольку без атомарности нельзя доказать достоверность истории. Его проверка обязательна до выпуска API.
3. T-07 зависит от наличия React. Пока интерфейс планируется, D-05 включён в комплект. Если интерфейс исключается, пересматриваем T-07/SR-11 и отмечаем неприменимость, а не успешную проверку.
4. До EK1 нужны содержательная проверка участниками по [распределению](CONTRIBUTIONS.md#распределение-s04), минимальная запускаемая основа, инструкция запуска и фиксация сдаваемой версии. В S04 эти действия не отмечены выполненными.
5. Защита файла SQLite от других пользователей ОС, внешнее сетевое развёртывание, регистрация и восстановление пароля за текущей границей продукта. При изменении границы пересматриваем модель, в том числе срок жизни и отзыв сессий.
