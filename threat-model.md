# Модель угроз

Эта модель относится к **TaskSpace**. Как устроен продукт и какие данные в нём важны, описано в [PROJECT.md](PROJECT.md). Требования безопасности и критерии их проверки — в [security-requirements.md](security-requirements.md).

## Как устроен продукт

```mermaid
flowchart LR
    User["Пользователь"]

    subgraph Client["Клиентский контур — ему нельзя доверять автоматически"]
        UI["Веб-интерфейс React<br/>"]
        Direct["Прямой HTTP-клиент<br/>.http или curl"]
    end

    subgraph Server["Серверный контур TaskSpace"]
        API["HTTP API ASP.NET Core<br/>"]
        EF["Entity Framework Core<br/>"]
        DB[("SQLite<br/>")]
    end

    User --> UI
    UI -->|"вход, ID сессии, ID объектов, тексты, решения"| API
    Direct -->|"те же HTTP-запросы"| API
    API --> EF
    EF --> DB
```



Пользователь сможет работать через React-интерфейс или посылать запросы в API напрямую. Для сервера это одинаково недоверенный клиент: он может изменить любой параметр, скрыть его или повторить запрос.

В API входят:

- данные для входа и идентификатор сессии;
- идентификаторы команды, задачи и участников;
- название и описание задачи, текст сдачи и замечание;
- действие автора: принять результат или вернуть его на доработку.

Сервер по действующей сессии определяет пользователя, проверяет его членство в команде и роль в задаче, а затем решает, можно ли выполнить действие. Веб-интерфейс к SQLite не обращается: с базой через Entity Framework Core работает только сервер.

**Что есть сейчас:** локальный API, файловая SQLite, React и автоматические проверки M1–M3. Фактические результаты прежней версии приведены в `docs/M2_*.md` и `docs/M3_CHECKS.md`.

**Расширение после EK1 (2026-10-23):** T-08–T-12 и планы D-06–D-09 добавляют доступность, ограничение ресурсов и восстановление. Они не реализованы и не подтверждены прежними тестами; тег `ek1` не меняется.

**Важные допущения:**

- Первая версия запускается локально. Публикация API в недоверенную сеть и доступ других пользователей ОС к файлу SQLite пока не входят в границу продукта.
- Ограничения в React не считаются защитой: сервер всё равно проверяет каждый запрос.
- Текстовые поля не поддерживают HTML и Markdown. React входит в локальную версию и показывает их как обычный текст согласно SR-11.
- D-01–D-05 реализованы в локальной версии; DOM-проверка D-05 использует HTTP-фикстуру, а не полный браузерный E2E. Новые D-06–D-09 — планы, не свидетельства.
- Сессия передаётся явным заголовком `Authorization: Bearer`, токен React хранится в памяти. Перехват действующего токена позволяет использовать сессию; генерация случайного значения защищает от угадывания, но не от уже произошедшей кражи. Ограничения этого решения приведены в D-01. Если меняем способ передачи на cookie, отдельно рассматриваем CSRF.



## Граница доверия


| Граница                | Что через неё проходит                                                                                                        | Почему сервер это проверяет                                                                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TB-01: клиент → сервер | Данные для входа, идентификатор сессии, ID команды, задачи и участников, параметры просмотра, текстовые поля и решения автора | Любой из этих параметров можно изменить в прямом HTTP-запросе. Сервер сам устанавливает пользователя по сессии, проверяет доступ к команде, роль в задаче и её текущее состояние. |
| TB-02: рабочая база → резервная копия и обратно | Предметные данные, учётные записи, контроль целостности копии | При восстановлении нельзя принять повреждённую/несогласованную копию или воскресить старые сессии. Операцию выполняет оператор ОС, не пользователь API; механизм D-09 пока запланирован. |

Сервер и SQLite находятся в одном локальном контуре. В модель добавлены ограниченный ресурсный бюджет локального процесса и аварийное восстановление оператором. Общая машина, недоверенный администратор, внешняя публикация и сетевой DDoS остаются за границей: для них понадобятся отдельные решения по HTTPS, правам ОС и сетевой защите.

## Что защищаем

Подробный список есть в [разделе 5 паспорта](PROJECT.md#5-значимые-данные-и-другие-объекты). Здесь важнее всего следующее:

- нельзя работать от имени другого пользователя;
- участник одной команды не должен видеть задачи и результаты другой;
- у задачи должны оставаться правильные автор, исполнитель и состояние;
- сдачи и решения нельзя подменить, потерять или выполнить как код в браузере другого участника;
- API должен сохранять доступность в объявленном профиле нагрузки, расход памяти/соединений/диска ограничивается;
- предметные данные должны восстанавливаться из пригодной копии с измеряемыми RPO/RTO (новый план).

## Приоритетный набор

Исходный приоритетный набор EK1 — **T-01–T-05**. После расширения в текущем плане приоритетны также **T-08, T-09, T-10**: доступность и ресурсы не защищены одними проверками роли. Для всего набора цепочки приведены в [сводке D](security-design.md#сводка-связей). Новые приоритетные меры ещё не реализованы — комплект не выдаётся за полностью защищённую версию.

T-06 и T-07 сохраняются со средним приоритетом; React входит в версию, поэтому T-07/SR-11/D-05 применимы. T-11 и T-12 средние из-за накопительного характера/реже возникающего события, но планы защиты включены.

## Уточнения S04

- T-01: D-01 закрывает отсутствие, подмену и угадывание сессии, а также раскрытие исходного пароля. Повтор уже украденного действующего токена остаётся риском до реализации SR-18/D-07; после их реализации риск сохраняется до отзыва или истечения срока. Сетевой перехват вне текущей локальной границы; путь к краже через пользовательский текст рассматривается в T-07/D-05. Перед внешним запуском модель пересматривается.
- T-06: учитываем не только одновременные запросы, но и старое действие из вкладки автора после возврата R1 и новой сдачи R2. Одинаковый статус «На проверке» не означает, что решение относится к той же сдаче. Контрпример, уточнение SR-06/SR-10 и проверка приведены в [D-04](security-design.md#пограничный-случай-старое-решение-и-новая-сдача). Приоритет остаётся средним, решение уже включено в комплект.
- Для всех приоритетных T-01–T-05 есть решения и планы проверки: D-01 — сессия, D-02 — команда и объекты, D-03 вместе с D-04 — полномочия, переходы и отсутствие частичной записи. Полный обзор связей — в [решениях](security-design.md#сводка-связей).


## Трассировка расширения и границы подтверждения

- T-08 → SR-12, SR-17 → D-06 → превышение частоты/параллелизма, большое и медленное тело, обслуживание второго клиента.
- T-09 → SR-13 → D-07 → лимиты логина и источника, восстановление входа после окна.
- T-10 → SR-14 → D-08 → ограниченные страницы, авторизация курсора и объём выборки на большой базе.
- T-11 → SR-15, SR-18 → D-08, D-07 → атомарная квота, SQLITE_FULL, очистка сессий.
- T-12 → SR-16 → D-09 → восстановление согласованной копии с измерением RPO/RTO.
- Уточнение T-01 → SR-18 → D-07 → истёкший/отозванный токен не принимается.

Это планы. Отсутствие лимитов установлено чтением кода, но успешная атака на доступность и соответствие новым порогам не проверялись. Эксперименты — только на изолированном локальном стенде с временной базой.
